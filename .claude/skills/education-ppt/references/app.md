# 앱을 생각한 원고 규칙

안드로이드 앱(나중에 PC 앱)은 **계획 단계**이고 시제품이 없다. 앱의 화면·자료 묶음·조작 엔진·설치 설계는 저장소의 `docs/app-design.md`(설계 메모)에 있다. 그 문서는 앱을 만들 때 읽고, 원고를 쓸 때는 이 문서만 읽는다.

정한 것: 안드로이드만, 스토어 없이 직접 설치한다. 부모 휴대폰과 아이 태블릿을 함께 쓰고, 기기 한 대 모드도 둔다. 학습 데이터는 앱과 떼어 낸 자료 묶음(원본 JSON + 미디어)이고 실행 코드는 넣지 않는다. 도형 옮기기·퍼즐·3D 보기·가상 실험은 앱의 엔진이 맡고, 묶음에는 장면 데이터만 넣는다.

**PPTX·활동지·부모용 안내가 기본 산출물이다.** 앱을 위해 이 세 가지의 내용을 줄이거나 바꾸지 않는다. 원본에 앱 전용 `app` 필드를 아직 넣지 않는다. 형식은 시제품으로 확정한 뒤에 정한다(`docs/app-design.md` ‘문항의 `app` 필드’).

## 1. 조작·실험 검토 (권장)

원고를 쓰거나 고칠 때, **조작·실험으로 학습 효과를 높일 장이 있는지** 검토한다. 앱이 없어도 PPTX 안에서 부모가 실물로 하는 활동을 더 잘 고르는 데 쓰인다.

1. **목표에서 시작한다.** 목표마다 “아이가 직접 움직이거나 바꿔 보면 더 잘 이해되는가?”를 묻는다. 그렇다고 볼 만한 경우는 다음과 같다.
   - 공간·모양을 머릿속으로 돌리거나 옮겨야 한다(도형의 이동, 입체·전개도, 지구와 달).
   - 양이 변하는 관계를 찾아야 한다(변인과 결과, 함수의 계수, 비율).
   - 눈에 보이지 않는 것을 보여야 한다(입자, 전류, 힘, 시간에 따른 변화).
   - 흔한 오개념을 직접 반박할 수 있다(무거운 것이 먼저 떨어진다, 분모가 크면 큰 수다).
   - 같은 꼴의 연습을 여러 번 해야 한다.
2. **효과가 작거나 해로운 경우는 거른다.**
   - 말·글로 따지는 것이 목표인 장(논증, 해석, 감상).
   - 실물·몸 활동이 더 나은 장(아래 2절).
   - 조작이 목표와 상관없이 재미만 더하는 경우.
   - 조작 방법을 익히는 데 시간이 더 드는 경우(초1·2는 조작 단계를 짧게).
3. **엔진과 흐름을 고른다.** 엔진은 `move2d`·`view3d`·`map`·`physics`·`react`·`circuit`·`model`·`dyngeo` 중에서 고른다(뜻은 `docs/app-design.md` ‘엔진 목록’). 흐름은 셋 중 하나다.
   - 예상 → 해 보기 → 설명(POE).
   - 구체 → 그림 → 기호.
   - 안내가 있는 탐구: 한 번에 변인 하나만 바꾼다.

   확인 문제는 조작 없이도 풀 수 있어야 한다.
4. **결과를 남긴다(권장).** 검토한 차시는 `interactive_review` 에 결과를 적는다. 쓰지 않기로 한 장도 까닭과 함께 적는다. 검사는 이 필드가 없다고 실패하지 않는다. 앱 시제품이 나오면 `priority: high` 장부터 장면을 만들고, 이 규칙을 그때 다시 정한다.

```json
"interactive_review": [
  { "slide": "S05", "engine": "move2d", "goal": "A", "flow": "구체→기호",
    "why": "조각을 직접 돌려 보면 합동 판단 오개념(M2)을 바로 반박할 수 있다", "priority": "high" },
  { "slide": "S09", "engine": null, "why": "논증 쓰기 장이라 조작이 목표와 무관하다" }
]
```

`priority` 의 뜻은 다음과 같다.

- `high`: 효과가 크고 다른 방법으로 대신하기 어렵다.
- `mid`, `low`: 그보다 덜하다.

검토자(1차·2차)는 다음을 본다.

- 검토 결과가 목표·오개념과 맞는가.
- 실물로 해야 할 것을 가상으로 바꾸지 않았는가.
- 꾸밈만 더한 것은 없는가.

**근거의 세기:** 가상 조작물은 수학 성취에 평균적으로 중간 정도의 효과가 보고되었다. 구체성 줄이기와 POE도 도움이 된다는 연구가 많다. 다만 규모가 작은 연구가 많아 ‘유망하다’ 정도로 본다. 시뮬레이션은 연구마다 결과가 엇갈리고, 안내 없이 맡기면 효과가 떨어진다. 출처는 `docs/app-design.md` ‘근거 자료’에 있다.

## 2. 실물이 먼저다

- **화면으로 대신하지 않는 것:** 실물 조작(바둑돌·콩 묶기·저울·물 붓기), 몸 활동(달리기·박·손 씻기), 실제 관찰(하늘·생물), 만들기·그리기, 역할극과 대화, 그림일기, 실험. 앱에서는 이런 장을 ‘짧은 안내 + 다 했어요’로 두고, 화면 속 놀이로 대신하지 않는다. 활동지는 종이로 둔다.
- **가상 실험은 다음 경우에만 쓴다.**
  - 위험하다(강산·강염기, 불, 전기, 높은 곳).
  - 집에서 할 수 없다(행성 운동, 미시 세계, 오래 걸리는 변화, 비싼 기구).
  - 변인을 여러 번 바꿔야 규칙이 보인다.
  - 실제 실험 전에 예상하거나, 실제 실험 뒤에 견준다.
- **실물과 가상을 함께 쓴다.** 연구에서 둘의 개념 학습 효과는 평균적으로 비슷하고, 함께 쓸 때 더 좋다는 보고가 있다. 무게·질감·힘의 느낌이 중요한 내용과 어린 아이에게는 실물이 낫다. 그래서 초등 저학년은 실물이 먼저이고, 가상은 보충으로만 쓴다.
- **모형의 단순화를 밝힌다.** ‘마찰 없음’ 같은 가정을 적고, 정리 단계에서 “실제로는 어떻게 다를까?”를 묻는다. 집에서 따라 하면 위험한 가상 실험에는 ‘집에서 하지 않음’을 적는다.
- **게임처럼 만들지 않는다.** 점수·별·시간 경쟁·보상 움직임과, 배울 것과 상관없는 꾸밈(캐릭터 움직임, 배경 효과)을 넣지 않는다. 꾸밈은 학습을 방해한다. 민감한 주제(신체 경계, 성 건강, 정신 건강, 중독, 폭력, 개인 정보)는 자동 채점 대신 부모와의 대화로 한다.

## 3. 지금 원고에서 앱을 도와 두는 습관

이 습관은 앱이 없어도 PPTX·안내서·진단지를 좋게 한다.

- **노트 정답을 문항 번호로 가른다.** 문항이 여럿이면 “① … ② … ③ …”처럼 번호마다 답을 적는다. `tools/plan/diagnose.py`(진단지)도 이 번호로 문항과 정답을 짝짓는다.
- **꼭 할 문제와 시간이 되면 할 문제를 노트에 나눠 적는다**(`home-tutoring.md`).
- **흔한 오답을 `misconceptions` 와 잇는다.** 노트의 ‘막히면’에 어떤 오답이 어떤 오개념인지 적는다.
- **소리로 구별하게 하는 문제를 내지 않는다**(ㅐ/ㅔ, ㅚ/ㅙ/ㅞ, ㅒ/ㅖ). 한글 단원의 예에서는 쓴 대로 소리 나지 않는 낱말(참외[차뫼], 열쇠[열쐬])을 피한다.
- **그림이 정답을 드러내지 않게 한다.** 문제 장의 그림 설명, 캡션, 칸 수가 답을 알려 주지 않는지 본다.

## 4. 앱 데이터 추출

`python3 tools/app/export.py G01` 은 원본에서 앱 데이터(임시 0판)를 뽑아 `build/app/G01/` 에 두고, 뽑지 못한 곳을 `report.md` 로 낸다. 보고서에 나온 곳은 앱 데이터가 아니라 **원본을 고친다**. 추출기가 기대하는 노트 정답의 꼴은 다음과 같다(부모가 읽기에도 좋다).

- **고르기:** 정답 첫머리에 보기 이름을 쓴다(“가.”, “나, 라.”, 차례는 “다 → 가 → 라 → 나”, 짝 찾기는 “[공] → 나”).
- **견주기:** 정답 첫 문장에서 맞는 쪽을 말한 사람·이름표로 밝힌다(“토끼가 맞습니다.”, “나.”). 친구의 말이 맞는지 묻는 장은 물음을 “친구가 바르게 읽었나요?”처럼 쓰고 “바르지 않습니다.”로 답한다. 판정이 없는 견주기는 “정해진 답보다 까닭을 봅니다.”처럼 밝힌다.
- **열린 문항:** 정답이 하나가 아니면 노트 `정답` 에 맞음 기준을 쓴다(“…을 말하면 맞습니다.”). 예상답만 두지 않는다.
- **여러 문항:** 문항마다 ①②③으로 답을 가른다(3절).
- **다른 맞는 답:** 괄호 안에 “(‘기뻐요’, ‘행복하다’도 맞음)”처럼 쓴다. 우리말 서술어는 한 꼴만 받으므로, 아이가 흔히 쓰는 다른 꼴(‘-요’ 꼴, 비슷한 말)을 적어 둔다.
- **풀이와 값:** 값을 앞에 쓴다(“31.4 cm(10 × 3.14)”). “10 × 3.14 = 31.4, 31.4 cm”처럼 풀이 끝 값을 다시 쓴 줄도 읽지만, 값부터 쓰는 쪽이 부모에게도 읽기 쉽다.
- **함께 쓰는 답:** 여러 문항이 같은 기준을 쓰면 “②③ 집의 물건에 따라 다릅니다…”처럼 번호를 붙여 쓴다(번호 뒤에 한 칸 띈다). “①②③을 …”처럼 조사가 붙으면 가리키는 말로 본다.
- **아이마다 다른 답:** “I get up at (아이의 시각).”처럼 괄호에 ‘아이의 …’를 쓰면 부모 판정으로 나간다.
- **한 노트 안 두 번호 체계:** 화면의 글이 ①②③으로 번호가 붙어 있으면 노트 정답에서는 그 문장을 “2번 문장”으로 부른다. 동그라미 숫자는 문항 번호로만 쓴다.

추출기가 붙이는 표시(앱이 읽음): `problem_index`(화면 `problems`·`review`의 몇 번째인지: 그림·식은 거기 있다), `figure_index`(끼운 문항의 그림), `parent_reads`(부모가 노트의 낱말·글을 읽어 준 뒤 답함: 소리 파일 없음), `cover`(본 뒤 가리고 쓰기), `wrong[].spoken`(입력 칸으로 칠 수 없는 오답: 부모가 들을 때 씀). 정리 장의 예상답은 말하기 물음의 답이라 복습 문항의 예시로 붙이지 않는다. 부모 판정 문항은 노트 정답 줄 전체를 `answer`로 내고, 정답·기준·예시가 하나도 없으면 ‘부모 판정 근거 없음’으로 보고한다.
